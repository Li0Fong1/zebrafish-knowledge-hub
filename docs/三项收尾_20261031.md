## 二、文献引用取不到（②）——两层根因，都已修

### 第一层：代码分支空转
`hub_orchestrator._run_literature` 里
`if gene_hits and yes is ready: ... elif gene_pool: <只打日志>`，
该分支**什么都不做**却截断了后面的全库检索，`pmids` 恒为 `[]`。
日志实锤：`[Hub] 基因文献已用 gene_pubmed 候选，不再做全库语义召回` 连续出现。

修法：删除空转分支；PMID 改为**先于**向量库就绪判断收集，并从 `bib["pmids"]` 兜底补充。

### 第二层（真正致命）：提问时按需加载 4B 向量库
`ncbi_gene_bibliography._yes()` 与编排器都调 `get_pubmed_yes_retriever()`，
只要向量库没加载就**当场加载** Qwen3-Embedding-4B + 170 个向量分片。实测：

- 加载耗时 **4.5 分钟**；
- 内存从 9GB 冲到 **36.8GB**（`mem_limit_mb=36864`，直接顶满）；
- 分片只装上 **31/170** 就被内存保护掐断；
- 请求 300 秒无返回，且 `available` 掉到 171MB，服务一度失联。

修法：改为**只取已就绪实例**（`peek`），不在提问路径触发加载；需要精排时用
`HUB_LITERATURE_EAGER_MODEL=1` 显式打开。标题本就来自 NCBI `esummary`，不依赖向量库，
因此引用照常输出。

### 验证（真实接口）
```
POST /api/chat  {"question": "tp53 在斑马鱼胚胎发育中起什么作用？"}
第 1 次：81.3s，答案 3318 字，尾部含 PMID 34991725 + 标题
第 2 次：30.4s，答案内 PMID 出现 12 次、去重 12 个
内存：mem_used_mb 9532（修复前 36863/36864），headroom 33546MB
```

## 三、隧道守护（③）

### 已做
- `hub_tunnel_guard.sh` 加固：`flock` 单实例、每 10 轮写 heartbeat、
  重建后原子回写 `tunnel_url.txt` 并记录耗时。
- 新增 `hub_tunnel_watch.sh`：每 60s 检查守护是否存活，不在则拉起
  （今天的教训：守护被外部信号打死过一次，纯 bash 循环自己不会复活）。
- 自愈实测：`kill -9` 隧道 → 日志 `pid-count=0 resetting` → **9 秒**拿到新地址 → 公网 200。
- 当前：`https://cream-supplies-interference-coast.trycloudflare.com`（`/` 200、`/static/js/app.js` 200、`/api/health` 200）。

### 未完成：地址永久固定
约束已逐项实测确认：

| 方案 | 结论 |
|---|---|
| 直接暴露公网端口 | **不可行**：`REDACTED_IP:8080` TCP 直连失败（`/dev/tcp` 不通；curl 的 502 是本地代理假象） |
| Cloudflare named tunnel | **需凭据**：服务器 `~/.cloudflared` 为空，无 `cert.pem`/`*.json`；`hub_guard.sh.bak-named-tunnel` 其实也是 quick tunnel（命名误导） |
| quick tunnel + 守护 | 已生效，但重建即换址 |

要真正固定，需要二者之一：
1. Cloudflare API Token（该域名在 Cloudflare 托管）→ 建 named tunnel，地址形如 `hub.你的域名`，永久不变；
2. 服务器开通 8080 入站（安全组/防火墙）→ 直接 `http://IP:8080`，地址永久不变。
