# 立项：内存护栏从「自杀式硬退」改为优雅重启

> 状态：已实施并上线。
> 关联审计项：可靠性 #14「内存护栏靠自杀重启」。

## 1. 旧实现的问题

```python
threading.Timer(2.0, lambda: os._exit(0)).start()
```

`os._exit()` 是**立即终止**：不执行 `finally`、不冲刷日志缓冲、不关闭数据库连接池、
不给网关留摘流窗口。后果：

1. 正在写的事务被硬切断（可能留下未提交/半写状态）；
2. 最后几秒的日志（恰恰是排查线索）丢失；
3. 进程消失瞬间，反向代理仍会把请求打进来，用户看到的是连接被重置，而不是
   「服务正在重启」这种可理解的提示；
4. supervisor 立刻拉起，冷启动约 20s，这段时间所有排队请求直接失败。

## 2. 新流程（四步）

```
触发：空闲 && 余量 < HUB_LOW_MEM_RESTART_MB
  ↓
① 置 _SHUTTING_DOWN 标志
   · /api/health → 503 {"status":"draining"}
   · /api/chat  → 503「服务正在重启以回收内存，约 20 秒后自动恢复」
  ↓
② 回收资源（后台线程，不阻塞请求线程）
   · gc.collect() + malloc_trim
   · MySQL 主/只读引擎 dispose（优雅归还连接）
  ↓
③ time.sleep(2) 让网关看到 draining，然后 os.kill(getpid(), SIGTERM)
   → uvicorn 正常 shutdown（关闭监听、等在途请求收尾）
  ↓
④ 若 grace_sec（默认 20s）后进程仍在 → os._exit(0) 兜底
   （保证「一定会重启」，不会卡在半死状态）
```

幂等：`_graceful_restart()` 用 `Event` 判重，并发触发只会执行一次。

## 3. 对外语义变化

| 场景 | 旧 | 新 |
|---|---|---|
| 重启窗口内 `/api/health` | 200 直到进程消失 | **503 `draining`**（网关/巡检应据此摘流） |
| 重启窗口内 `/api/chat` | 连接重置 / 502 | 503 + 明确文案（含"约 20 秒"） |
| 日志 | 可能丢尾部 | 完整 |

**注意**：如果网关把 503 当作"实例不健康"直接踢掉，行为是正确的（摘流）；
如果监控按 200 判活，需要把 `status=draining` 视为"计划内重启"，不要告警。

## 4. 配置

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `HUB_LOW_MEM_RESTART_MB` | 1200 | 低于此余量且空闲才重启；`0` = 关闭自动重启 |
| `grace_sec`（代码参数） | 20 | SIGTERM 后等待秒数，超时才兜底硬退 |

## 5. 验收

1. 正常运行时 `/api/health` 返回 200 `{status: ok}`。
2. 手工把 `HUB_LOW_MEM_RESTART_MB` 调到高于当前余量、且无问答在跑：
   - 日志出现 `[内存] 空闲且余量 …：进入优雅重启（摘流 → 释放资源 → SIGTERM）`；
   - 紧接着 `/api/health` 返回 503 `draining`；
   - supervisor 拉起新进程，`/api/health` 恢复 200。
3. `HUB_LOW_MEM_RESTART_MB=0` 时不再触发重启（回滚验证）。

## 6. 未解决（需另立项）

根因是「模型常驻 ~31GB / cgroup 36GB / 并发 3」的余量本来就薄。
优雅重启只是把"重启过程"做干净，不改变"需要重启"这件事。
真要消除，需要：模型量化/换小模型、按需加载、或拆分推理进程与 API 进程。
