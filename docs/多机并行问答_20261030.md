# 多机并行问答（并发闸开放）— 2026-10-30

## 目标

让多台机器 / 多个浏览器标签**同时提问、各自独立返回**，不再"一问在跑、其余排队到 503"。

## 两个根因（缺一不可）

### 根因 1：并发上限被钉死在 1

`agent/chat_gate.py` 里 `MAX_CONCURRENCY` 默认 1，`.env` 也没有覆盖。
历史注释给出的理由是「单次问答峰值 RSS ≈ 27GB，cgroup 上限 36GB，并发 2 必然 OOM」。

**这个结论把两件事混为一谈了**：27GB 是「35 个 FAISS 向量分片首次被访问时懒加载」的
**一次性成本**，不是每个请求的**边际成本**。当时按"每请求 27GB"算计，自然只能开 1 车道。

### 根因 2（更隐蔽）：车道 key 用错了身份

`lane_from_request()` 原优先级是 `访问令牌 > Hub 会话 > 浏览器会话 > IP`。

但 `x-access-token` 是 **`.env` 里的全站访问口令（WEB_ACCESS_TOKEN）**，所有访客同一个值。
于是每台机器的 lane 都被算成 `u:<同一个token>` → **全部挤进同一条车道** →
即使把并发调到 8，调度器看到的仍然是"同一个人的连续提问"，只会串行。

实测证据：4 个不同会话并发提交，`/api/health` 返回 `chat_queue_lanes` 只有 1 条。

## 内存实测：并发数该怎么定

在 32 核 Xeon Gold 6144 / cgroup 上限 36.8GB 上，把"一次性"和"边际"拆开量：

| 项目 | 实测值 |
|---|---|
| 冷进程 RSS（刚拉起） | 0.5 ~ 2.7 GB |
| 跑满不同主题后常驻工作集 | **≈ 31.7 GB**（曲线在 31.66GB 走平，不是泄漏） |
| 索引就位后单请求边际增量 | **≈ 60 MB**（2.67 → 2.73GB 峰值） |
| 一次 183s 问答的 CPU 累计 | 约 20s（其余 160s 在等远程 DeepSeek API） |
| 真实余量 | 36.8 − 31.7 ≈ **5.1 GB** |

所以并发上限的正确算法是 **`余量 ÷ 单请求安全垫`**，不是"每请求 27GB"。
按每请求留 ~1.5GB 垫子，3 车道（≈4.5GB）是这台机器的稳妥值。

索引懒加载有双检锁保护（`get_rag()` / `get_pubmed_yes_retriever()` / `get_shared_embedding()`），
冷启动后多台机器同时提出第一个问题，也只会加载一份，不会 ×N。

## 改动清单

| 文件 | 改动 |
|---|---|
| `agent/chat_gate.py` | `MAX_CONCURRENCY` 默认 1 → **3**，注释改写为上述实测依据 |
| `agent/chat_gate.py` | `lane_from_request()` 优先级改为 **Hub 会话 > 浏览器 session-id > token > IP** |
| `api/api_server.py` | 低内存护栏不再无条件 `os._exit(0)`：还有人跑就只让新请求排队，**空闲时才重启清堆** |
| 服务器 `.env` | `CHAT_MAX_CONCURRENCY=3`；`HUB_PUBLIC_URL` 校正为当前隧道地址 |
| `.env.example` | 并发说明同步 |

> `api_server.py` 部署时**没有整文件覆盖**：服务器版的 liftover 端点与本机不一致
> （本机有 `TARGET_BUILD` / `ROUTES` / `BUILD_ALIASES` 完整实现，服务器版是旧写法）。
> 只把护栏这一处 patch 进服务器版，liftover 逻辑一行未动。

## 验证结果

4 个不同会话（同 token、不同 session-id）同时提交，`chat_gate` 上限 3：

```
run=3 q=1 lanes=3     ← 出现 33 次：3 个真并行，第 4 个自动排队
run=3 q=0 lanes=3     ← 出现 18 次
m1 http=200 t=123s    ← 并行完成
m0 http=200 t=183s    ← 并行完成（若串行，它必须 ≥306s）
m3 http=200 t=393s    ← 排队后第二批
m2 http=200 t=397s
RSS 峰值 31.06GB（余量 5.8GB，未触发护栏）
```

关键判据：前两个请求 123s / 183s 就回来了。串行的话第二个不可能是 183s。

## 遗留

1. **隧道地址未固定**（quick tunnel 每次重建换域名）。`HUB_PUBLIC_URL` 是启动时读的，
   隧道重建后需同步；长期方案是命名隧道（要 Cloudflare API Token）或机房开放 8080 入站。
2. **本机与服务器 `api_server.py` 的 liftover 端点存在分歧**，下次部署前必须先比对，
   否则会把线上 liftover 回退。本机版看起来更新。
3. 若要再提并发：需先扩 cgroup 上限（现 36.8GB），否则 4 车道的安全垫不够。
