方案索引常驻模型 + 系统8 车道安全垫合计结论
A. 全量索引直装（170 片）≈100 GB12.5 GB12 GB≈125 GB 128 GB 才稳 96 GB 会 OOM；这正是线上只装 31–36 片的物理原因
B. 部分索引（约 60 片）35 GB12.5 GB12 GB≈60 GB 96 GB 够 但只覆盖约 35% 文献，回答标 partial
C. 索引量化（SQ8 / IVF-PQ）≈25 GB12.5 GB12 GB≈50 GB 64 GB 即可全量语义覆盖；代价是 3–5 天重建 + 召回需 A/B 验证（项目已有 100 题基准）
D. 拆模型服务（1 模型节点 + N 应用节点）100 GB（模型节点）应用节点仅 2 GB按节点算— 应用节点可横向扩到 8–16；但要改代码（嵌入/重排走 HTTP），工程量 1–2 周

每片常驻怎么来的：线上 35 片时 RSS 31.7 GB，减去模型 9.5 GB 与应用 ~1.5 GB ≈ 20.7 GB，折合 0.59 GB/片；170 片 ≈ 100 GB（含 pickle 与堆开销，磁盘上只有 58.4 GB，内存占用高于磁盘是 FAISS + Python 对象的正常现象）。

判定「支撑住了」的四条硬指标：① 8 个 session 同时提交，/api/chat/queue 的 chat_running=8, chat_queued=0；② P95 ≤ 150 s；③ /api/health 的 mem_headroom_mb 始终 > 3000；④ 全程 0 次 exited code=137、0 次 524。
