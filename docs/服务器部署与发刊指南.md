## 1. 项目概览



### 1.1 系统定位



斑马鱼基因问答体是一个 **物种专用 AI 研究助手**，采用三模块融合架构：



| 模块 | 作用 |

|------|------|

| **MySQL 功能基因库** | 基因基础信息、表达量、GO、同源、文献引用（`gene_reference`） |

| **RAG 文献知识库** | PubMed / Europe PMC / WoS 摘要向量检索（FAISS + BGE） |

| **本地大模型** | Qwen-0.5B（轻量/SQL）+ Qwen-7B Q4（深度推理，llama.cpp） |



智能体按问题意图自动路由：数据库查询、基因详情、RAG 问答、BLAST、富集分析等。



### 1.2 当前数据规模（约 2026-06）



| 数据 | 规模 |

|------|------|

| `gene_basic` | ~32,526 基因 |

| `gene_expression` | ~71 万条 |

| `gene_go` | ~11 万条 |

| `gene_alias` / `gene_xref` | ~10 万 / ~7 万 |

| 文献 RAG（采集中） | Europe PMC 广搜约 **17 万+** 命中，持续入库 |

| `gene_reference` | 增量关联中（菜单 15，从 catalog 提取基因–PMID） |



### 1.3 启动菜单速查



| 编号 | 功能 |

|------|------|

| 2 | Web 界面（默认 8080） |

| 11 | 文献 RAG 广搜采集（Europe PMC 镜像，全量 zebrafish） |

| 15 | 文献→基因关联（`gene_reference`，可与 11 并行） |

| 8 | 构建基因别名 / ID 映射 |

| 13/14 | 导出/导入 CSV 清洗数据 |

## 3. GPU 云服务器推荐（发刊 + 长期运行）



> **原则**：选有 SLA、支持包年、可自动备份的云厂商；**不要**用按小时短租 GPU 平台做对外长期服务。



### 3.1 首选：阿里云



| 组件 | 推荐规格 |

|------|----------|

| **GPU 应用机** | **ecs.gn7i** 系列（**NVIDIA A10 24GB**）· 8 vCPU · 32 GB 内存 |

| **系统** | Ubuntu 22.04 LTS |

| **磁盘** | 系统盘 100 GB ESSD + **数据盘 500 GB ESSD** |

| **云数据库** | **RDS MySQL 8.0**：4 核 8 GB · 200 GB · **自动备份 7 天** |

| **网络** | 固定带宽 5～10 Mbps + Nginx HTTPS |

| **计费** | **包年 1～3 年**（长期更省） |



**参考成本**：约 **2500～4500 元/月**（含 GPU 机 + RDS + 磁盘 + 带宽，包年更低）



**优势**：SLA 正式、发刊 Methods 可写明部署环境；A10 24GB 跑 7B 余量充足；RDS 与算力分离，数据更安全。



### 3.2 备选：腾讯云



| 组件 | 推荐规格 |

|------|----------|

| **GPU 机** | **GT4**（T4 16GB）· 8 核 · 32 GB 内存 |

| **磁盘** | 300～500 GB 高性能云硬盘 |

| **数据库** | **TencentDB MySQL 8.0** · 2～4 核 8 GB · 自动备份 |



**参考成本**：约 **1800～3200 元/月**



**说明**：T4 可跑 7B Q4，但文献采集 + RAG 重建 + 多人 Web 同时跑时余量不如 A10。



### 3.3 高配（多人访问 / 审稿演示）



- **GPU**：A10 24GB 或 A100 40GB  

- **内存**：64 GB  

- **磁盘**：500 GB～1 TB ESSD  

- **对象存储 OSS/COS**：定期备份 SQL、文献 catalog、FAISS 索引  



**参考成本**：**5000～12000+ 元/月**



### 3.4 不推荐



| 类型 | 原因 |

|------|------|

| AutoDL / 恒源云按小时 | SLA 弱，不适合发刊对外长期服务 |

| 纯 CPU 无 GPU | 7B 推理过慢，演示体验差 |

| Windows Server GPU 版 | 授权贵，Python 栈在 Linux 更优 |

| 单机无备份 | 审稿期数据丢失风险高 |

## 8. 论文 Methods 参考表述（英文草稿）



> 可根据期刊格式微调。



**System deployment.** The Zebrafish Gene QA system was deployed on an Alibaba Cloud GPU instance (NVIDIA A10, 24 GB VRAM, 8 vCPUs, 32 GB RAM) running Ubuntu 22.04 LTS. Structured genomic data were stored in MySQL 8.0 (Ensembl GRCz11, release 116; NCBI taxon 7955). Literature abstracts mentioning *zebrafish* or *Danio rerio* were retrieved via Europe PMC and Web of Science and indexed using FAISS with BGE-small-zh-v1.5 embeddings. Gene-centric queries were answered through a hybrid pipeline combining SQL-backed structured retrieval, retrieval-augmented generation (RAG), and local large language models (Qwen-0.5B for lightweight routing/SQL; Qwen-7B-Chat Q4_K_M for reasoning via llama.cpp with GPU acceleration).



**Data sources.** Gene annotations, expression, GO terms, and cross-database identifiers were integrated from Ensembl, NCBI Gene, ZFIN, and Bgee. Literature-gene associations were extracted from indexed abstracts and stored in a relational reference table (`gene_reference`).

## 补充（2026-10-05）：线上 OOM 崩溃循环的根因与处置

> 这一节是后来补的，用于覆盖前文"根因待确认"的表述。结论均已实测。

### 现象
站点间歇 502；`<RT>/logs/hub_guard.log` 每 2~3 分钟一条 `hub health=000 -> restart`（自 2026-09-30 起）。

### 根因（实测证据）
| 证据 | 读数 |
| --- | --- |
| `<BASE>/api/api_server.py` 所属进程 | uvicorn 跑在 `…/user-1005.slice/user@1005.service/app.slice/run-*.scope` |
| cgroup 上限 | `user-1005.slice` 的 `memory.max = 38654705664`（36 GB）；该 scope 自身为 `max`，**上限在上一级** |
| OOM 计数 | `memory.events` → `oom_kill` 持续增长（714 → 760） |
| 进程特征 | `logs/hub_supervise.log` 里 **没有** `hub exited code=` → 不是自身崩溃，是**进程组被秒杀**（连守护一起带走），故无 traceback |
| 内存曲线 | 重启后 RSS 20 秒内 27.2 GB → 30.8 GB |
| 触发者 | 启动预热 PubmedYes（Qwen3-Embedding-4B + 多分片 FAISS + CrossEncoder）与 RAG/重模型**并行** |

### 修复（已上线，哈希校验一致）
1. `api/api_server.py`：内存闸门（逐级向上找 cgroup 上限；余量 = 上限 − anon）+ `HUB_PUBMED_WARMUP` 默认 0（不预热重资源）+ 预热串行化 + `/api/health` 暴露 `mem_*`。
2. `rag/pubmed_yes_retriever.py`：分片按内存预算加载（`PUBMED_YES_SHARD_RESERVE_MB`），返回 `shards_total/partial`。
3. `rag/rag_builder.py`：`_normalize_device()` 修掉"cuda:* 在无 GPU 机上必失败 + 同一嵌入模型双载"。

### 效果（实测）
存活从"~90 秒必死"变为**连续 13.5 小时**；RSS 19 GB；负载 0.13；CPU 0.5%；守护不再频繁重启。

### 运维必读
- `deploy/hub_guard.sh` 由 **root cron 每分钟**执行；`deng` 无 `crontab` 权限 → **手工杀掉 Hub 会在 1 分钟内被拉起**，要停服必须让管理员摘掉 cron。
- 公网地址默认来自 **cloudflared 快速隧道**，**每重启一次换一次域名**；权威来源 `<RT>/public_url.txt`。
- **要固定地址用命名隧道（已就绪）**：本机跑 `scripts/setup_named_tunnel.py`（需自备一个域名并 NS 到 Cloudflare），
  它会把 `config.yml` 放到 `<RT>/cloudflared/`；`hub_guard.sh` 检测到该文件即自动切成命名隧道，
  域名取自其中的 `hostname:`（**永久不变**，不再需要从日志里抓）。删掉该文件即退回快速隧道。
- cloudflared 二进制已从 `/tmp`（**重启会丢**）迁到持久目录 `<RT>/bin/cloudflared_run`，守护优先使用它。

### 遗留决策（未擅自改）
**2026-10-09 更正**：先前写的“线上 `FAISS_PUBMED_YES_DIR` 未设置 → 解析到不存在的默认路径（0 分片）”**是误判**——`.env` 里该键本来就有值（指向 `faiss_pubmed_yes_qwen3_4b_v2_merged`，170 分片 / 63 GB），只是 `.env` 由 `core/entry.py` 在启动时写进 `os.environ`，所以 `/proc/<pid>/environ` 里看不到；用不带 `.env` 的 `python -c` 探测才会看到不存在的回退默认值。

真实情况与现状：
- 索引已接入；线上只能常驻一部分分片（实测 `shards_loaded=32/170`、`partial:true`），因为全量 63 GB > 用户 slice 36 GB 上限。论文数字取全量索引，不受影响。
- 共享服务器省资源档（已上线）：`HUB_WARMUP_RAG=0`（启动只留轻量模型）+ `HUB_PUBMED_WARMUP=0` + `PUBMED_YES_SHARD_RESERVE_MB=6000` + `EMBEDDING_DEVICE=cpu`；空闲 RSS 由 35.2 GB 降到 **2.5 GB**，显存 0。
- `pubmed_status` 里的 `on_demand` = “按配置不预热，属正常”；`low_mem` = 内存不够而放弃（告警）。省资源档下 `pubmed_ready=false` 是预期，**不要**在此档跑按 `pubmed_ready` 判活的看门狗脚本。
- 要覆盖全量分片，仍需三选一：①抬高 `MemoryMax` 到 80G；②接受部分加载（现状，已返回 `partial`）；③重建更小索引（量化/降维）。
