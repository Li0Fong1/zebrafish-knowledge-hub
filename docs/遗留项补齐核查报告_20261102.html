二、三项各自是怎么修的

1. DOI / PMID 核验车道（llm/citation_verify.py，新增）

根因不是模型编造，是检索错位：路由只看句中有没有基因词，看到 DOI 里的 s41586 这类片段就进了基因详情链路，用户要的那篇论文从未被检索。

接管条件是两个都要成立：句中有 DOI/PMID 实体 + 问法指向「这篇论文本身」。 这样「DOI 的命名规则是什么」「页面上哪里填 DOI」这类概念题与界面题不会被抢； 光给一串 10.1038/... 不带问法也不接管。

查询要过两张表：先 literature_paper，未命中再查 ncbi_gene_bibliography—— 后者正是基因卡片右侧那 10 条参考文献的来源。只查第一张会出现自相矛盾： 用户刚在卡片上看到 PMID，转头问「这篇讲了什么」，系统答「不在库里」。

  • 命中：给出库内真实题名 / 期刊 / 年份 / PMID，并说明库里有没有全文。
  • 未命中：明说「不在本 Hub 文献库」，给 doi.org 或 PubMed 链接让人自查， 不猜题名、不猜结论。
  • 库连不上：单独一句话，不与「没有收录」混为一谈（见下面这个坑）。

2. 数据口径提问

触发条件是认出了具体页面 + 出现口径词（TPM / FPKM / 单位 / 归一化 / 「是 X 还是 Y」）。 页面别名做闸门是必要的：如果只认口径词，「TPM 和 FPKM 的区别是什么」这种纯概念题 也会被当成界面问题，那是另一种答非所问。

同时把两个页面的文案补实了：表达页写明只有 Bgee 的 0–100 置信分与 Expression Atlas 的 TPM， 不提供 FPKM / RPKM / read count，也没做跨样本归一化；基因页写明坐标单位是 bp。

3. 序列接口从 50.9s 降到 18.2s

原来的判断「启动子走 Ensembl 所以慢」只说对了一半。真实原因是两跳请求 × 默认重试： 一个基因要先 symbol → 坐标、再 坐标 → 序列，每跳超时 25s、重试 3 次， 最坏 75s，早已超过 45s 的总预算——所以用户拿到的其实是「超时」，而不是「Ensembl 这次没答上来」。

改成每跳单次 25s、只重试一次（两跳 50s 内可走完），再加结果 TTL 缓存与基因解析缓存。

踩到的坑：第一版把超时收到 12s，结果——测得更快了（18.9s）， 但启动子直接变成「获取失败」。这类优化不能只看耗时，必须同时看功能是否还在。 最终留 25s，功能与速度都保住。

三、修的过程中新发现的两个问题

库把「查不了」说成「查过了没有」

MySQLClient.execute_sql 失败时不抛异常，而是返回 {"success": False}。 核验模块第一版只取 .get("data") or []，于是数据库连不上时会拿到空列表， 顺理成章地回答「这篇不在库里」——把故障说成了事实。这恰好是这轮要防的那类错误， 已抽 _query() 显式断言 success，连不上就直说连不上。

库里有脏记录：DOI 与期刊对不上

实测 10.1371/journal.pbio.2002226（PLOS Biology 的 DOI 前缀）被挂在 Comparative biochemistry and physiology 期刊的一篇 GSTp2 论文上。 这是库数据本身串了行，不是模型编的，但如果原样输出，就等于替错误记录背书。

处理方式：核验命中行按 DOI 去重（库里同一篇常有多条，期刊大小写不同、PMID 有无不同）， 并对归属明确的 DOI 前缀做一次「前缀 vs 期刊」比对，对不上就在答文里标出这条记录可疑， 而不是把元数据当事实转述。对不出归属的 DOI 一律不表态，避免误报。

五、仍然没做到的部分

  • 核验只认本地库，不联网。所以「库里没有」不等于「这论文不存在」—— 答文已经这么措辞，但没有做 DOI 在线解析。要做真存在性核验，得接 doi.org 内容协商， 这会引入外网依赖与延迟，本轮没动。
  • 脏数据只做了提示，没做修复。库里那条串行的 DOI 仍在，答文只能标出可疑， 根治要回查数据导入流程（literature_store.upsert_paper 的字段映射）。
  • 「表达数据怎么算出来的」还答不了。现在能说清单位与来源，但 Bgee 置信分的具体计算口径、 Expression Atlas 的定量流程，库里没有存，不会编。
  • 序列首次仍要 18s。缓存只帮重复请求；首次耗时取决于 Ensembl 当时的响应速度， 要做稳定低延迟得本地化基因组序列，那是另一件事。
