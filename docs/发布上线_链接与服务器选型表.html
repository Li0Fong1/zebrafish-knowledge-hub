2固定链接方案对比：五种给地址的方式

「固定」= 重启、换机、隔月再发都不变的地址。只有 ①②③ 满足；④⑤ 仅适合临时内测。

3服务器规格：三档够用即可

关键前提——大模型走 DeepSeek API，机器只跑嵌入/重排/检索/Web，所以选 CPU 机型，不选 GPU 机型。

档位CPU / 内存磁盘可承载月费参考说明
最低可用 4 核 / 16 GB 100 GB SSD 1–2 人 ¥100–250 能跑起来，但 4B 嵌入 + 索引一加载就贴内存上限，会频繁触发保护、答案走「部分装载」
推荐（发刊/演示） 8 核 / 32 GB 200 GB SSD 4–8 人 ¥500–900 与现有线上环境同级，热态 9.5 GB 有余量；并发闸开 4，演示/审稿完全够
充裕（团队常用） 16 核 / 64 GB 500 GB SSD 15–20 人 ¥1200–2000 可把 63 GB 全量索引常驻，去掉 partial；顺带跑文献采集与重建
可选：加 GPU 8 核 / 32 GB + A10 24G 500 GB SSD — ¥2500–4500 仅当要完全本地大模型（数据不外传 / 断网可用）。否则纯浪费预算

系统建议 Ubuntu 22.04 LTS；同机装 MySQL 8.0 可省 RDS 费用，但发刊期建议每日 mysqldump 到对象存储。

6风险与对策：六个已经踩过或必然会踩的坑

风险触发条件 / 证据影响对策
共享服务器不可控 现宿主机非自有、无 root；hub_guard.sh 的 root cron 已失效 管理员一清理，站点直接消失，无法申诉 路线 A 只作过渡；发刊前迁到自有服务器（路线 B）
内存装不下全量索引 全量 63 GB > cgroup 36 GB，线上实测只装 31/170 片 回答标 partial，召回不全 三选一：内存抬到 64 GB / 接受部分装载 / 重建更小索引（量化或降维）
Cloudflare 100 秒超时 单问 30–80 s，长答接近 80 s，余量薄 偶发 524，前端表现为「答案中途断了」 改「立即返回任务号 + 轮询结果」；或自有服务器走 Nginx 直连、不经 CF 代理
冷启动首问极慢 实测冷启动 238 s，预热后 ~50 s 重启后第一位访客以为站点坏了 保留 POST /api/warmup + 巡检冷态自动预热；对外公告「首次访问较慢」
密钥与凭据泄露 .env 含 DeepSeek Key、MySQL 密码、SSH 密码 API 被刷、数据库被清 权限 600、绝不入 git；服务器用独立只读 DB 账号；上线前轮换一次 Key
笔记本当服务器 本机仅 16 GB 内存，休眠/断网/家宽无固定 IP 夜里必然掉线，链接再固定也没用 本机只做开发；对外一律用 7×24 机房机器
